# 빗길 차선 AR HUD — 핸드오프 문서

작성일 2026-09-04

이 문서 하나로 현재 상태를 파악하고 이어서 작업할 수 있도록 정리했습니다.
세부 절차는 각 항목에서 가리키는 개별 문서를 보세요.

---

## 1. 프로젝트 개요

젯슨 오린 나노에서 빗길 차선을 추론하고, 그 결과를 라즈베리파이가 받아
HUD 모니터에 그린 뒤 반사 필름으로 전면 유리에 띄우는 대회 시제품입니다.

```
젯슨 오린 나노                       라즈베리파이
─────────────                       ──────────────
카메라 (룸미러 옆)
  ↓
차선 추론 (기존 코드)
  ↓
차선 폴리라인 좌표
  ↓  UDP 5005 / JSON            →   좌표 수신
                                     ↓
                                   운전자 시점 정렬 (호모그래피)
                                     ↓
                                   AR 오버레이 렌더
                                     ↓
                                   7인치 HUD 모니터
                                     ↓
                                   반사 필름 → 전면 유리
```

인식과 표시를 **UDP 좌표로 완전히 분리**한 것이 이 구조의 핵심입니다.
모델이 없어도 HUD 작업을 끝낼 수 있고, HUD가 없어도 추론 작업을 할 수 있습니다.
영상은 전송하지 않고 좌표만 보내므로 대역폭 부담이 거의 없습니다.

## 3. 명령 정리

```bash
# 화면 구성
python3 hud_ui.py preview [--theme] [--windowed]   # 모델·네트워크 없이 화면만
python3 hud_ui.py sample  [--theme] --out png      # 상황별 PNG 저장
python3 hud_ui.py receive [--theme]                # 실제 수신 + 표시
python3 hud_ui.py bench   [--theme]                # 이 장치 렌더 속도 측정

# 운전자 시점 정렬
python3 hud_align.py place                         # HUD가 찍은 자리에 꼬깔 놓기
python3 hud_align.py pick --frame road.png         # 영상에서 꼬깔 클릭
python3 hud_align.py aim                           # 운전석에서 십자 맞추기
python3 hud_align.py verify                        # 확인과 미세 조정
python3 hud_align.py preset --write-image 보정판.png # 시뮬레이터용
python3 hud_align.py eyebox                        # 머리 위치 조준 표시
python3 hud_align.py profile --name tall           # 현재 보정을 이름 붙여 저장
```

`--theme` 없이 실행하면 단순 흰 선 표시, 붙이면 AR 오버레이 시안입니다.

## 6. 운전자 시점 정렬 — 핵심 개념

이 프로젝트에서 가장 중요한 부분입니다.

### 왜 필요한가

카메라는 카메라 위치에서 도로를 보고, 운전자는 눈 위치에서 봅니다. 두 시점이
다르므로 카메라가 본 차선을 그대로 그리면 실제 도로와 어긋납니다. 모니터를
움직여서는 해결되지 않습니다. 필요한 것은 사다리꼴 왜곡 보정이고, 이건
소프트웨어에서 미리 반대로 찌그러뜨려야 상쇄됩니다.

### 왜 행렬 하나로 되는가

차선은 노면 위에 있고 노면은 평면입니다. 그래서

```
카메라 영상 → 노면 → 운전자 시점 → HUD 패널
```

전체가 평면 대 평면 대응이고, 호모그래피끼리 곱해도 호모그래피이므로
**최종 결과는 3×3 행렬 하나**입니다. 카메라 장착 위치, 눈 높이, 반사 각도,
좌우 반전이 전부 이 행렬에 흡수됩니다. 각각을 따로 재거나 모델링할 필요가 없습니다.

합성 데이터로 검증했을 때 재투영 오차가 0.002픽셀 이하였습니다.

### 어떻게 구하는가

노면 위 같은 지점을 카메라 영상에서 한 번, HUD 화면에서 한 번 찍어 대응쌍을
6개 모읍니다. `cv2.findHomography` 가 행렬을 풉니다.

순서는 두 가지이고 **A 를 권장**합니다.

- **A (`place` → `pick`)**: HUD가 점을 찍어주면 그 자리에 꼬깔을 놓습니다.
  HUD가 자기 커버 범위를 직접 알려주므로 거리를 잴 필요가 없습니다.
- **B (`pick` → `aim`)**: 꼬깔을 먼저 놓고 HUD 십자를 거기에 맞춥니다.
  꼬깔이 HUD 범위 밖이면 맞출 수 없습니다.

`S` 를 누르면 표식별 재투영 오차가 픽셀 단위로 출력됩니다.
**평균 5픽셀 이하가 목표**이고, 15픽셀을 넘으면 뭔가 잘못된 것입니다.

자세한 절차는 `HUD_시점정렬_사용법.md`.

## 7. 사람이 바뀔 때

시연에서 여러 명이 앉는다면 매번 전체 보정을 반복할 수 없습니다.
위쪽이 더 확실합니다.

1. **눈 위치 고정 (권장)** — `eyebox` 로 링을 띄우고, 보정한 사람 시점에서 링이
   겹쳐 보이는 자리에 앞유리에 스티커를 붙입니다. 다음 사람은 링과 스티커가
   겹치게 좌석을 조절합니다. 10초면 되고 추가 장비가 없습니다.
2. **프로필 블렌딩** — 키 큰 사람과 작은 사람으로 각각 `profile` 저장 후,
   `verify` 에서 `-` `=` 로 사이를 섞습니다. 중간 눈높이에서 오차 0.4픽셀로
   검증했습니다.
3. **통째로 밀기** — `verify` 에서 `W A X D`. 가장 빠르지만 평행 이동뿐이라
   눈높이가 10cm 이상 차이나면 한계입니다.

**시연 준비**: 대표 한 명으로 전체 보정 → `profile --name main` → 체격이 다른
한 명으로 한 번 더 → `profile --name tall` → 스티커로 아이박스 표시.

## 8. 시뮬레이터 시연

게임 화면 자체가 평면이고 차선이 그 위에 있으므로 같은 논리가 그대로 적용됩니다.
실차보다 유리한 점은 화면에 보이는 **모든 것**이 같은 평면이라 전부 정렬된다는 것입니다.

- **화면 캡처 방식 (권장)**: `preset --write-image` 로 보정판을 만들어 게임
  모니터에 전체화면으로 띄우고 `aim` 만 하면 끝입니다. 좌표를 이미 알고 있어
  촬영과 클릭이 필요 없습니다.
- **물리 카메라 방식**: 실차와 절차가 같습니다. `pick` → `aim`.
  이때 `preset` 은 쓰면 안 됩니다.

**주의**: 게임 카메라 시점(보닛뷰/실내뷰)이나 FOV 를 바꾸면 보정이 무효입니다.
시연 전에 확정하고 잠그세요. 화면이 1~2m 앞이라 실차보다 시차가 커서
아이박스 고정이 더 중요합니다.

## 9. AR 오버레이 시안 구현

전달받은 디자인 문서의 하이파이 시안 `2a`(기본 주행) / `2b`(이탈 경고)를
OpenCV 로 구현했습니다. 문서의 좌표·색·타이밍 값을 그대로 따랐습니다.

### 상태 머신

| 상태 | 진입 조건 | 표시 |
|---|---|---|
| `BOOT` | 기동 후 1.2초 | 경계선 드로잉 + 틱 상승 스윕 |
| `LOCKED` | 기본 | 시안 `2a` |
| `LOW_CONFIDENCE` | `confidence < 0.45` | 리본 60% 감광, 경계선 점선, 칩 앰버 |
| `DEPARTURE` | `warning` 이 `departure_*` | 시안 `2b`, 이탈 측만 강조 |

### 문서와 다르게 구현한 것

**거리 틱과 페이드 기준**이 가장 큰 변경입니다. 문서는 틱을 `503/428/360/296/240/198`
에 고정했는데, 이는 리본이 화면 바닥까지 내려온다는 전제입니다. 실제 HUD 는 도로의
좁은 띠(앞 5~40m 정도)만 덮어서 그 y 값들이 리본 바깥에 떨어집니다. 처음 돌렸을 때
틱이 하나도 안 보였습니다. 그래서 문서의 y 를 **리본 안의 상대 위치**로 환산해
`0.100 / 0.304 / 0.489 / 0.663 / 0.815 / 0.929` 로 씁니다. 문서 Open questions
3번(거리 매핑 재산출)에 대한 답이기도 합니다.

**크롬 자동 회피**: 같은 이유로 정합 칩이 리본과 겹쳐서, 칩과 상태 스트립이
리본 밖으로 비켜나게 했습니다. `theme.chrome_avoids_ribbon` 으로 끌 수 있습니다.

**가산 합성**: HUD 는 발광 디스플레이라 겹치는 빛이 밝아집니다. 알파 합성 대신
가산으로 쌓습니다. 광학계 동작과 맞고 6배 빠릅니다.

**패널 배경은 보이지 않습니다**: `rgba(5,7,10,.55)` 는 거의 검정이고, 반사식
HUD 에서 검정은 투명입니다. 상태 스트립과 배지는 테두리와 글자만 보이는 게 정상입니다.

**그라디언트와 글로우**: OpenCV 에 없어서 직접 만들었습니다. 그라디언트는
마스크에 세로 알파 램프를 곱하고, 글로우는 축소 → 블러 → 확대 → 가산입니다.

## 10. 성능

1024×600 기준, 개발 환경에서 프레임당 **12ms** 입니다. 처음 91ms 에서 세 단계로
줄였습니다.

| 최적화 | 효과 |
|---|---|
| 합성을 마스크 바운딩 박스로 제한 | 91 → 32ms |
| 채널 분리 가산 합성 | 32 → 13ms |
| 글로우 1/3 축소 후 블러 | 위에 포함 |

**라즈베리파이에서 반드시 직접 재세요.**

```bash
python3 hud_ui.py bench --theme
```

33ms 를 넘으면 순서대로 시도합니다.

1. `theme.glow_scale` 3 → 4~5 (효과 가장 큼, 글로우가 뭉개짐)
2. `theme.glow_gain` 1.6 → 0.8
3. `theme.glow_gain` 0 (블러 연산이 통째로 빠짐)
4. `display.width/height` 낮추기

젯슨 추론이 22fps 라면 HUD 가 그보다 빨라도 표시는 갱신되지 않습니다.
30fps 를 목표로 잡고 남는 여유는 글로우 품질에 쓰세요.

## 11. 추론 코드 연결

```python
from hud_ui import HudUiSender

hud = HudUiSender("192.168.50.20", 5005)

# 추론 반복문 안에서
hud.send(
    lane_polylines_px,
    frame_width=frame.shape[1],
    frame_height=frame.shape[0],
    warning="none",             # none / departure_left / departure_right
                                # change_left / change_right
    confidence=0.82,            # 0~1, 게이지와 LOW_CONFIDENCE 판정
    departure_distance=0.0,     # m, 배너 부제
    lkas=True,
    acc=True,
    fps=22.4,
    inference_ms=44.6,
)

hud.close()                     # 종료 시 한 번
```

이미 0~1 정규화 좌표면 `frame_width`, `frame_height` 를 빼면 됩니다.
차선을 못 찾았으면 빈 배열을 보내세요. `status` 가 `lost` 로 잡혀 즉시 지워집니다.

### 이탈 판정

```python
LANE_CENTER_NEUTRAL = 0.5   # 반드시 측정해서 채웁니다
DEPARTURE_MARGIN = 0.10
HOLD_FRAMES = 5

offset = (left_x + right_x) / 2 - LANE_CENTER_NEUTRAL
if offset > DEPARTURE_MARGIN:
    warning = "departure_left"
elif offset < -DEPARTURE_MARGIN:
    warning = "departure_right"
```

**`LANE_CENTER_NEUTRAL` 을 0.5 로 두면 안 됩니다.** 카메라가 룸미러 옆이라
차량 중심선에서 벗어나 있어, 차선 한가운데 있어도 계산된 중심이 0.5 가 아닙니다.
차선 한가운데 똑바로 정차한 상태에서 수십 프레임 평균을 내서 채우세요.

경고가 떨리면 같은 조건이 5프레임 연속될 때만 켜고, 끌 때는 10프레임 정도
버티게 하면 깜빡임이 줄어듭니다.

## 12. 기존 코드에서 고친 것

**`seq` 리셋 버그.** 원본 `hud_system.py receive` 는 마지막 `seq` 보다 큰 패킷만
받는데 그 값을 되돌리는 코드가 없었습니다. 추론 코드만 재시작하면 `seq` 가 0 부터
시작하는데 수신기는 여전히 이전 번호를 기대해서, **HUD 가 영구히 검은 화면으로
남습니다.** `hud_ui.py receive` 는 패킷이 끊긴 것으로 판정되는 순간 이 값을
초기화합니다.

**방향키 코드.** 원본 `calibrate` 는 방향키를 81~84 로 잡았는데 이는 대문자
`Q` `R` `S` `T` 의 아스키 코드와 겹칩니다. 리눅스 GTK/Qt 빌드는 보통
65361~65364 를 반환합니다. 새 도구들은 `W A X D` 문자키를 기본으로 하고
두 방향키 인코딩을 모두 받습니다.

## 13. 알아둘 한계

**노면 위에 있는 것만 정렬됩니다.** 앞차나 표지판처럼 노면에서 떨어진 물체는
이 행렬로 맞지 않습니다. 차선만 그리는 지금 구성에서는 문제가 없습니다.

**눈 위치 하나에만 맞습니다.** 머리를 움직이면 시차로 어긋납니다.
좌석을 조정하거나 운전자가 바뀌면 7번 항목의 방법을 쓰세요.

**HUD 는 도로의 일부 구간만 덮습니다.** 아주 가까운 노면과 지평선 근처는 화면
밖으로 나갑니다. 코드가 잘라서 그리니 오류가 아니라 정상입니다.

**보닛 가림.** 카메라를 높이 달면 보통 앞 4~6m 부터 노면이 보입니다.
`place` 로 십자를 찍을 때 여섯 자리가 전부 카메라 영상에도 보이는지 확인하세요.

## 15. 설정 파일 요약

`hud_config.json` 한 파일에 전부 들어갑니다.

```json
{
  "display":   { "width": 1024, "height": 600, "fullscreen": true,
                 "flip_horizontal": false, "smoothing_alpha": 0.55 },
  "network":   { "bind_host": "0.0.0.0", "port": 5005,
                 "packet_timeout_seconds": 0.35 },
  "alignment": { "mode": "correspondence", "camera_horizon_y": 0.0,
                 "horizon_margin": 0.18, "pan_x": 0, "pan_y": 0,
                 "blend": 0.0, "pairs": [], "profiles": [] },
  "ui":        { "style": "ar_overlay", "safe_area": [0.06,0.06,0.94,0.94],
                 "lane": {}, "warning": {}, "debug": {} },
  "theme":     { "glow_sigma": 3.2, "glow_gain": 1.6, "glow_scale": 3,
                 "edge_width": 4.0, "alert_edge_width": 8.0,
                 "boot_animation": true, "chrome_avoids_ribbon": true }
}
```

`alignment.mode` 가 `correspondence` 면 실측 정렬을, `quad` 면 예전 방식을 씁니다.
정렬 전에도 화면 구성 작업이 가능하도록 `quad` 가 기본값입니다.
`camera_horizon_y` 는 0이면 보정 데이터에서 소실선을 자동으로 계산합니다.
